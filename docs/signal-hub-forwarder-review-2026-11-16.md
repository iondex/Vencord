# Forwarder 与 Signal-hub 复审、修复和后续规划

日期：2026-11-16（Asia/Shanghai）。复审基线：`808f0d02`，分支 `local`，远端跟踪 `iondex/local`。本文汇总前两轮规模评估、五项发现、本轮获授权的 1/3/5 修复和下一阶段规划。生产投递快照另见 [生产核对记录](signal-hub-production-2026-11-16.md)。

## 范围与生产边界

本轮只修改 Forwarder 的故障恢复、Remote 默认地址及相关设置、测试和文档。服务端 Local/Remote 合并尚未实现。Channel-logger 已按用户要求退出后续维护和改造范围；下文只保留历史规模及可靠性边界，不安排其重构。Transcribe 保持独立，不改变注册、录制、转录和投递行为。

不停止、重启或注入运行中的 Discord 和 Signal-hub，不清库、不修改生产配置、不自动释放或重发结果不明的任务。已有本机队列、精确 durable ACK、防自循环、富文本、去提及和每日清理契约保持原有语义。用户原有根 `pnpm-lock.yaml` 修改不纳入提交。

## 五项发现及处理

### 1. 首次落盘失败缺少恢复和明确状态：本轮修复

原来成功落盘后的消息能重试，但首次写入失败只会抛错，不能等同于已可靠入队。现在保留临时文件写入、文件 fsync、rename、目录 fsync 的顺序，同时加入有界的进程内恢复缓冲：最多 256 条或 16 MiB，先到者为限。

未落盘的 enqueue 返回 `ok: false, durable: false`，单独统计数量、字节数、最早时间、安全错误码及超额拒绝数量。界面展示错误；Native console 在故障首次发生、恢复及停止时记录英文日志，不输出消息正文或凭据。缓冲满的严重日志按 30 秒限频，拒绝计数持续增长。

既有 drain 先重试落盘，再进行 HTTP 交接；原 eventId、捕获时间及序列化 body 保持不变。每恢复 25 条让出事件循环。transport 停止后不清空内存缓冲；有未落盘消息时禁止切换运行目录，同目录重配置可以继续恢复。失败写入清理本次临时文件，避免反复堆积 `.tmp`。

边界：内存缓冲不是持久存储，Discord 崩溃、退出或整机断电会丢失尚未落盘的部分；超过容量的采集会明确被拒绝。初始化阶段连 client-id 都无法持久化时仍无法正常启用采集。独立采集机告警和历史补采不能由这次小补丁替代。

### 2. Channel-logger 队列仅在内存：记录边界，退出后续范围

历史复审确认其服务离线时保留内存队列并退避，没有持久化和总容量限制，进程退出会丢失未交接部分。不能把它视为 Forwarder 持久队列的等价副本。根据用户之后的明确指令，不实现、不安排该插件后续改造；原规划阶段 F 撤销。

### 3. Remote 默认主地址与协议错配：本轮修复

原 Remote 默认主地址指向 Local `49321/forward`，却发送 legacy payload，本地 v2 接口会拒绝，然后才尝试 CF。新默认主地址为 `https://forwarder.yufeng.run/forward`，备用默认为空。已保存的自定义地址不覆盖；若 Remote 主地址与 Local 地址相同，设置页显示简短提醒。

Remote 继续采用 `source/notification/metadata/message` 和既有 nullable 兼容，不改为 v2。Local 不自动 fallback 到 CF。服务地址可以指向本机或内网机器。

### 4. Remote 重试和告警不能原样搬入 Hub：暂不实施

原 Remote 每条消息独立重试，最终失败逐条调用钉钉，没有跨消息故障合并和冷却。HTTP 2xx 只证明请求获得成功响应，未证明每个 Discord 目标送达。迁移时应复用 Hub 持久调度、尝试记录和合并告警，不叠加“外层任务重试 × 内层五次请求”。本轮保留过渡期行为。

### 5. 本机隔离记录缺少受控重交：本轮修复

隔离文件保留原始 body；新增独立原因旁路记录，包括 reason、body hash 和时间。设置页汇总原因，提供“重交可恢复记录”按钮，只有用户主动操作才会重排。

可重交候选为明确拒绝的 HTTP 400/413/422，且必须通过 envelope 校验、原 body hash 校验、eventId 与文件名校验，并确认 pending/acked 不存在同名记录。先修复地址、版本或大小限制，再操作。重交只是移回原 pending 队列，仍须得到精确 durable ACK，不直接发送 Discord。

HTTP 409、损坏记录、缺少原因元数据的历史记录、文件被修改和同名 pending/acked 均保留检查，不自动重放。重复隔离保留两份原始文件，并将双方标记为 `capture_conflict`，禁止盲重交；不覆盖旧证据，也不让冲突记录持续阻塞后续消息。旁路原因记录在重交后保留；旧隔离记录不会被伪造为可恢复记录。Hub 的投递修复 worker 仍只负责服务端任务，不能越过采集机隔离区。

## 必须保持的现有契约

- Local 基础过滤掉非 server 消息、自己发送、乐观消息和显式排除 server，其余消息原样交给 Hub。不要引入 Discord 通知资格筛选。
- Hub 全量归档，通过 route 生成任务；固定配置快照并执行当前安全检查。五分钟 CF 同步失败继续使用本地有效缓存；没有有效缓存时先保存。
- 投递首次尝试后重试五次，指数退避并尊重更长的限流；耗尽后由持久扫描任务恢复。结果不明先对账，不能直接重发。
- 防循环包括来源/目标拓扑、显式排除 server、输出身份和输出消息记录、未完成发送意图。不能为了省事过滤全部 Bot。
- 正文、Markdown 和 Embed 尽量保留，移除用户/角色/频道提及和来源频道链接，不增加来源标记。发送身份沿用目标配置。
- 插件每天上海时间 20:00 只清理已交接副本；Hub 数据库全量保留。运行日志保留第三方日志库的 JSONL、英文简洁彩色 console、七天轮转压缩。

## 后续架构规划：先评估，未实施

目标链路：插件基础过滤 → 本机 durable spool → Hub 全量归档与审计 → Local 或 Remote 后端。插件只配置 Hub 地址、可选连接令牌、排除 server、连接检查和统计。Hub 初期只增加全局 `local/remote`，不增加每条 route 的后端、多套队列框架或通用插件平台。

Local 保留本地渲染、信号解析及 Discord 发送。Remote 按原始消息创建一次 CF 交接任务，组装 legacy 协议；不能把 v2 直接 POST 给旧 Worker，不能把本地渲染分段逐一交给 CF，也不能在两端重复替换正文、选择身份或解析 Signal。

Remote 预筛 enabled、server、channel、sender 和安全条件。正文关键词及其他策略只有与旧 Worker 语义核对后才能复用。统一采集后不再依赖 Discord `shouldNotify`，范围会比旧 Remote 更全面，必须在迁移说明和验收中显式确认。

每个任务固定 backend、endpoint 和配置依据；全局模式切换只影响新任务。Remote 结果不明时不能切到 Local 重发。主备 endpoint 也须遵守同一重复投递约束。一次调度执行只做一次 CF 请求，由 Hub 决定后续退避。

先核对旧 Worker 的幂等键、接收回执、逐目标送达回执和查询能力，再定义可承诺的保证。监控区分“本地已保存、等待交给 CF、CF 请求成功、结果不明、目标确认送达”；没有回执时不得把请求成功计为目标送达。

五分钟本地 route 缓存与 CF 实时配置可能漂移。记录本地版本和远端响应，不声称本地快照约束了 CF 最终目标。可以评估近期未匹配记录的有限重判，但不能自动回放全历史、测试过滤或时间截止之前的消息。

Remote 缺少 Local 的实际输出 message ID 和发送意图证据，需要补 CF Bot/Webhook 身份及目标频道/thread 回流兜底，继续校验路由环与来源/目标重叠。仅识别已知输出，不能屏蔽新闻来源 Bot。

| 阶段 | 范围 | 验收与回滚边界 |
| --- | --- | --- |
| A：固定生产基线 | 版本、配置、构建、实际收发统计 | 不变更运行协议和积压任务；保留本次脱敏记录 |
| B：采集故障诊断与恢复 | 本轮 1/3/5，小范围补丁 | 故障注入、容量限制、隔离安全、ACK、每日清理；可独立回滚 |
| B2：生产问题独立处理 | Webhook uncertain 核对、Signal 凭据、告警及补采能力 | 先查证，不盲重发；与架构迁移分开 |
| C：服务端 Remote 后端 | legacy 适配、单次交接任务、持久调度 | 老插件继续工作；Local 默认行为保持 |
| D：Remote 安全和回执 | 防回流、结果不明、配置漂移与统计 | 先证明不重复，再扩大生产范围 |
| E：插件收敛 | 删除 Remote 发送/重试/告警设置 | 已有 spool 可继续使用，受控切换，Native 完整重启验证 |

后续结构可分为入口采集及生命周期、设置界面、Native 通信、持久队列四块。过滤和序列化保持简单函数，不合并不同插件队列。原先 900～1,100 行的估计只描述迁移后的大致规模，可靠性补丁增加代码属于有明确目的的增量，最终不以压行数验收。

## 本轮验证和启用

回归先在旧实现复现落盘失败、缺失重交入口和默认值错配，再验证修复；额外复现并修复隔离同名覆盖。测试覆盖内存容量、原 eventId/body 保留、同目录重配置、409/损坏/历史隔离保留、hash 和文件名校验、已有 pending 防覆盖、损坏元数据及每日清理。

具体命令和结果见 [验证记录](signal-hub-validation.md)。开发构建不会自动重载已运行的 Native。完整退出并重开 Discord 后新补丁才会加载；已有注入无需再次 inject。Signal-hub 服务端代码未变，本轮不重启服务。
