# Signal-hub 实现进度与复审

日期：2026-11-15。复审范围为 `local` 分支相对 `a276f10a` 的实现，包括新文件；随后按用户授权分批提交并推送到 `iondex/local`，发布记录见 `signal-hub-validation.md`。没有创建 issue 或 PR。需求来源为当前会话及 `signal-hub-plan.md`，文档统一放在 `docs` 根目录。

## 实现进度

- 仅注册并默认启用 `forwarder`、`channel-logger` 两个可选功能插件，保留上游必需 core/API。
- Local 插件负责基础过滤、原始采集、磁盘 outbox 和可靠交接，支持本机和内网服务。路由、存储、Signal、配置同步和补发均在独立服务中。
- 已有 SQLite 归档、配置离线缓存、投递队列、防自循环、只读 logger/Bot 补采、日志、告警、状态 API 和备份。
- 统一启动入口为 `pnpm hub:configure` / `pnpm hub`，默认运行目录为 `signal-hub/var`；支持通过环境变量配置监听、端口、CF 地址和插件可访问地址。
- 新增逐 route 决策、逐次尝试记录、五次指数退避重试及每分钟修复扫描；详见运行说明。
- 尚未生产接管、真实 Discord/Bot 权限验收或调用模型；语音功能只完成探索。二进制媒体归档、目标外观重建、人工安全释放工具和 ACK 自动清理尚未实现。

## Standards

此轴按 AGENTS 的简单实现、职责边界和稳定性要求检查；以下属于有运行证据支持的设计判断，并非工具可检查的风格违规。

1. **P2：关闭后被尚未完成的 configure 再次启动。** Native 配置等待当前发送结束后，没有检查这期间是否收到更新的 stop/configure。已用请求序号取消过期配置，保留 stop 的优先级。
2. **P2：client-id 写入中断后无法重新启动采集。** 原实现直接创建最终文件，空文件或部分写入会使后续配置一直失败。已改为原子发布、目录 fsync，并修复不完整的身份文件；有效身份继续保留。
3. **P2：250ms 调度反复全表扫描历史消息。** 已增加待处理/延迟消息索引，新增尝试记录和对账表也有对应活跃状态索引，避免保留历史越多、空闲扫描越慢。

保持一套 SQLite 持久化调度，没有引入外部消息队列、额外路由层或插件内业务处理。重试计数和到期时间落在原 jobs，快重试和定时补发复用同一个发送入口。

## Spec

1. **P1：CF 配置更新让旧任务永久等待。** 旧任务使用最新目标校验，修改目标后既不能投旧目标，也没有重建新任务。已按“重试不因下一轮同步改变内容或目标”固定快照；当前禁用/来源/暂停/排除与防回流仍能否决执行。
2. **P2：logger 失败阻断 Bot 补采。** 两来源原来共享回调，logger 抛错后 Bot 不会执行。已改为各自独立调度和故障报告。
3. **P2：早期 uncertain 记录饿死后续对账。** 原查询总取最早 50 条。已过滤无法按 Bot nonce 确认的 webhook 记录，并用持久化游标轮转 Bot 记录。

本地 Signal 与 CF 参考代码核对时另修正三类兼容问题：模型输入绕过路由替换且缺少引用上下文边界；期权白名单错误使用合约 ticker；指数信号被改投而漏掉主目标。现在共享文字处理、限制模型输入为 12000 字符、标记 REPLY CONTEXT，按 underlyingTicker 匹配白名单，并按 SPY/QQQ/SPX/IWM 向主目标及指数目标投送相同内容。

兼容要求专指插件 remote 在过渡期继续向旧 CF Worker 发送通知消息；保留通知资格、legacy envelope、主备接收模式。Local 使用独立协议，不模拟旧 Worker，也不自动回退 CF。冻结旧 schema 测试覆盖四类 nullable 400、回复、server/guild 兼容别名和富消息字段；新 CF 分支的相同契约只是额外参考证据。

追加复审修复了钉钉告警逐条发送、进程重启限频丢失、未发送故障也发恢复、单目标成功错误解除其他故障及 watchdog 心跳损坏无法通知的问题。现在按严重/普通级别合并通知，严重故障快速通道不受普通冷却阻拦，持续严重/普通故障分别每 5/30 分钟提醒；状态及退避持久化。增加归档/已到期待发积压监控、按原消息追踪、隔离原因统计，以及本机 outbox 的积压和 ACK 可见性。

分批发布后修复了模式选择与实际 native 初始化不同步的问题：插件启动时固定运行模式，修改 `Local` / `Remote` 选项后在重启前继续使用原模式。设置页展示实际运行模式和待重启提示，两个模式的状态组件各自管理 React hooks，避免切换选项时改变同一组件的 hooks 顺序。插件停止后忽略残留消息回调，回归测试验证两向切换及基础过滤。

## 新增投递保证机制

每个命中启用 route 的消息记录处理结论，包括策略拦截、未知类型和冲突。正常任务记录目标、配置快照、分段、次数和到期时间；每次检查/HTTP 尝试记录结果，成功记录 Discord message ID。

确定失败先做首次尝试后的五次重试，退避 1/2/4/8/16 秒，尊重更长的 429 等待时间。耗尽后保留 `retry_wait`，最早五分钟后由每分钟扫描任务重新调度。失败任务和尝试记录不因重启消失；模型 SDK 内部重试关闭，避免叠加重试层。

已发请求但结果不明确时进入 `uncertain`，扫描器先对账，不能无证据自动重发。安全暂停、过期 Signal 和策略拦截也不会被补发任务绕过。这是可追踪、可恢复的投递机制，不是外部系统恰好一次的承诺。

## 验证与边界

### 第二轮 Standards 复审

审查固定范围为 `a276f10a...c1c7b5fa`。以下 3 项属于职责分散或重复策略导致的实际故障，均为结构判断，不是格式工具可检查的规范违规；最严重为 P2，均已修复：

1. **P2：当前路由冲突只拦新消息，不拦已有任务。** 规划要求唯一匹配，执行检查却只判断旧 route 是否仍在匹配集合中。执行前现在同样要求当前唯一 route 与固定 route 一致，普通发送和 Signal 均不能绕过新引入的冲突。
2. **P2：重试意图沿用旧发送身份。** 被明确拒绝的 webhook 任务改用 Bot 后，upsert 只更新状态，丢失了按 Bot nonce 对账的机会。现在每次记录发送意图都更新实际身份；历史身份仍保留用于防回流。回归覆盖 webhook 拒绝、切到 Bot、响应丢失及最终对账成功。
3. **P2：进程在发送期间退出，严重告警可能缺失。** `recoverLeases` 从磁盘恢复 uncertain，但告警创建只在 sender 的异常分支。健康刷新现在根据持久化 uncertain 状态创建和解除同一个严重告警。

### 第二轮 Spec 复审

需求依据为 `signal-hub-plan.md` 与运行说明；3 项均已修复，最严重为 P1，未发现需处理的范围扩张：

1. **P1：状态无法写盘时 watchdog 不发通知。** 规划要求“此时由 watchdog 显示本地错误并尽力直接通知”。写状态的异常原来在网络请求之前终止整轮检查；现在状态写入单独容错，仍尽力通知，当前进程以内存保留限频和恢复状态。磁盘故障期间无法承诺跨 watchdog 重启的去重。
2. **P2：消息接收与任务规划之间可能换配置。** 规划要求“有 active revision 的新事件在入库时绑定该版本”。新增消息入库即绑定快照，规划按该版本处理并按批次缓存验证结果；当前安全规则仍可否决。无配置/route 冲突的明确待处理状态可在配置修复后重新绑定。旧库事务迁移保留原始消息、已建任务和配置，历史未记录的接收版本只能绑定迁移时的有效版本。
3. **P2：新任务可能持续抢占到期补发。** 运行说明要求到期修复工作交回同一发送池。新任务原来以零时间排序，永远早于 epoch 时间的重试；现在初始到期时间为入队时刻，旧任务迁移为对应消息时间，使已到期补发与新任务按时间公平竞争。

### 第二轮结构整理

初始化、类型校验、环境变量覆盖及私密配置读取集中到 `runtime.ts`；主入口负责命令分派和运行调度。watchdog 复用目录/告警配置读取，但不依赖主服务的配对令牌有效，环境变量也可提供独立告警凭据。主服务配置不合法时在打开数据库前报错；状态和备份仍可用于配置损坏后的诊断。

统一 shell 入口新增 status、backup、watchdog，并暴露 `pnpm hub:status` / `hub:backup` / `hub:watchdog`。启动回归在临时目录执行真实 CLI 与 mock CF，覆盖从其他目录运行、缺少数据库、非法配置、令牌保留、三个运维命令以及 SIGTERM 退出。

实际命令和最新结果见 `signal-hub-validation.md`。本轮新增启动/退出、配置快照、CF 兼容、逐 route 审计、五次退避、修复调度、对账公平性及重启迁移测试。没有向生产 `/forward`、Discord、模型或钉钉发送测试内容。

完整 lint 仍存在仓库原有的相对导入规则及 installer 文件头问题，不作为已通过；本轮改动其余风格检查单独验证。用户已有根 lockfile 改动未修改。

初始两轴复审各发现 3 项，均已修正。Standards 轴最严重为关闭竞态/身份写入/扫描性能三项 P2；Spec 轴最严重为配置刷新使投递任务滞留的 P1。CF 语义修复和新增需求另列，未混入两轴计数。
